## 🎯 核心问题：ADR 的真实价值

### ADR 是什么？

Architectural Decision Record（架构决策记录）是一种轻量级文档，记录：
- **何时** 做了架构决策
- **为什么** 选择这个方案（而不是其他选择）
- **什么** 是长期后果

### ADR vs ARD（架构设计文档）

| 维度 | ADR | ARD |
|------|-----|-----|
| **目的** | 记录 **决策过程** | 记录 **当前设计** |
| **时间点** | 决策发生时 | 项目存档时 |
| **内容** | 选择+拒绝理由 | 完整系统设计 |
| **格式** | 轻量级（1-2页） | 详细（5-50页） |
| **更新频率** | 减少更新 | 频繁更新 |
| **查阅者** | 未来的开发者 | 当前团队 |
| **例子** | "为什么选 PostgreSQL？" | "系统整体架构图" |

## 📋 不同项目类型的文档矩阵

### 1️⃣ **初创小项目**（1-3 个月，<5 人）

```
必须有：
✅ PRD          (user stories, acceptance criteria)
✅ 实施计划      (tech stack 决策, 任务拆分)

可选：
⚠️ ADR         (只在关键决策点)
⚠️ ARD         (简化版, 主要是架构图)

不需要：
❌ 详细 ADR 集合
❌ 完整 ARD
```

**理由**: 快速迭代，团队小，记忆力好，文档负担过大

---

### 2️⃣ **成长期项目**（3-12 个月，5-20 人）

```
必须有：
✅ PRD          (完整需求)
✅ 实施计划      (分阶段)
✅ 实施进度      (持续跟踪)
✅ ADR          (关键决策 3-5 条)
✅ ARD/规范      (高层架构)

可选：
⚠️ 详细 ADR 集合 (>5 条)
```

**理由**: 团队扩展，需要知识转移，决策需要记录

---

### 3️⃣ **企业级项目**（1+ 年，20+ 人）

```
必须有：
✅ PRD          (详细需求库)
✅ 实施计划      (详细拆分)
✅ 实施进度      (精细跟踪)
✅ ADR          (完整决策集合, >10 条)
✅ ARD          (完整架构文档)
✅ API 规范      (接口定义)
✅ 部署文档      (DevOps)

可选：
⚠️ C4 架构图     (多层次图表)
⚠️ 数据字典      (数据模型)
```

**理由**: 长期维护，知识转移关键，合规要求

## 🤖 LLM 工作流中的文档角色

### 你当前的工作流

```
PRD (用户需求)
  ↓
LLM 分析 PRD
  ↓
实施计划 (分阶段计划)
  ↓
LLM 实施
  ↓
实施进度 (跟踪)
```

### ADR 如何融入 LLM 工作流

#### 场景 1：ADR **存在** 时

```
PRD 中有不清楚的设计选择
  ↓
查看相关 ADR (为什么做这个决定？)
  ↓
LLM 基于 ADR 上下文理解设计意图
  ↓
✅ 更准确的实施计划
  ↓
✅ 减少错误重构
```

**收益**: LLM 输出质量提升 20-30%

#### 场景 2：ADR **缺失** 时

```
PRD 中的设计选择
  ↓
LLM 不知道为什么这样设计
  ↓
⚠️ 可能重新讨论已决策的选择
  ↓
⚠️ 浪费 token 和时间
  ↓
❌ 低效的实施计划
```

## 🔍 何时才真的需要 ADR？

### ✅ 你应该写 ADR 的情况

| 情况 | 示例 | 优先级 |
|------|------|--------|
| 重大技术选择 | "为什么选 PostgreSQL 而不是 MongoDB？" | 🔴 高 |
| 架构模式变更 | "迁移从单体到微服务" | 🔴 高 |
| 权衡决策 | "性能 vs 可维护性：选择了后者" | 🟡 中 |
| 长期有效的决策 | "API 版本管理策略" | 🟡 中 |
| 团队扩展时 | 新人加入需要了解设计前提 | 🟡 中 |
| 争议性决定 | "为什么不用流行的框架 X？" | 🟡 中 |

### ❌ 你不需要写 ADR 的情况

| 情况 | 示例 | 理由 |
|------|------|------|
| 显而易见的选择 | "用 Python 写后端" | 没有争议，无需记录 |
| 临时决定 | "这个版本用方案 A，下版本改" | 不是长期有效的决策 |
| 已在 PRD 中记录 | "需求文档已清楚说明" | 避免重复 |
| 短期项目 | "<3 个月，团队 <3 人" | 文档负担过大 |
| 框架约定 | "用了 Spring Boot，默认用它的规范" | 框架已做决定 |

## 🎨 推荐的文档体系设计

### 按项目生命周期阶段

```
┌─ 规划阶段 (Week 1-2)
│  └─ PRD (需求定义)
│
├─ 设计阶段 (Week 2-4)
│  ├─ ARD (高层架构设计)  ← 缺失！建议补充
│  └─ ADR-001, ADR-002... (关键决策)
│
├─ 实施阶段 (Week 4-12)
│  ├─ 实施计划 (下达给开发者/LLM)
│  └─ 实施进度 (持续更新)
│
└─ 运维/演进 (Month 3+)
   ├─ ADR-003... (新增决策)
   └─ ARD (更新)
```

### 三叉体系（推荐）

这是最平衡的方案，尤其适合**高效团队**和**LLM 辅助开发**：

```
1. PRD（产品需求文档）
   - 用户故事
   - 接受准则
   - 业务价值
   
   ↓ (LLM 参考)

2. ARD（架构设计文档）- ⭐ 你缺这个
   - 系统架构图 (C4 Level 1-2)
   - 核心组件和交互
   - 数据流
   - 高层技术选择说明
   
   ↓ (LLM 参考)

3. 实施计划（分阶段实施）
   - Phase 1, 2, ... (按优先级)
   - 每个 Phase 的具体任务
   - 技术实施细节
   
   ├─ 选项 A：也记录 ADR（5-7 条关键决策）
   │  └─ 适合：中等项目，长期演进
   │
   └─ 选项 B：跳过 ADR（轻量级）
      └─ 适合：快速项目，稳定技术栈
```

## 📝 立即行动方案

### 第 1 步：创建 ARD（架构设计文档）Agent

创建 `.github/agents/architecture-design.agent.md`：

```markdown
---
name: "Architecture Design Documentation"
description: "Create comprehensive architecture design docs (ARD) with system diagrams, component descriptions, and design rationale."
---

# Architecture Design Documentation

## 包含内容

1. **High-level Architecture Diagram** (C4 Level 1-2)
   - Components and their relationships
   - Data flow
   
2. **Component Design**
   - Key components description
   - Component responsibilities
   - Technology stack per component

3. **Data Model**
   - Entity-relationship overview
   - Key tables/collections
   
4. **Design Decisions & Rationale**
   - Why this architecture?
   - Key technology choices
   - Trade-offs

5. **Integration Points**
   - External systems
   - APIs
   - Dependencies

Output: `/docs/architecture/architecture-design.md`
```

### 第 2 步：保留 ADR（可选但推荐）

当你需要记录关键决策时，使用现有的 `create-architectural-decision-record.prompt.md`

建议记录：
- 技术栈选择（框架、语言、数据库）
- 架构模式（单体 vs 微服务）
- 安全策略
- 数据存储策略

### 第 3 步：整合到 LLM 工作流

在 PRD Agent 或实施计划 Agent 中添加提示：

```
如果存在 ARD，LLM 在生成实施计划时应：
  1. 先读 ARD 理解整体设计
  2. 参考 ADR (如果有) 理解设计决策
  3. 确保实施计划与 ARD/ADR 对齐
  4. 在实施计划中标注架构依赖
```

```
✅ PRD

### 扩展体系（按需）

⚠️ API 规范 (如果有对外 API)
⚠️ 部署文档 (运维需要)
```

### 为什么不需要完整 ADR 集合？

1. **你有 PRD**: 已经记录了需求和交取准则
2. **你有实施计划**: 已经记录了技术决策和步骤
3. **你用 LLM**: 可以快速重新讨论决策，不像人工团队那样需要完整历史
4. **你的项目规模**: 中等项目，关键决策 <10 条，ADR 集合收益不大

### 何时转向完整 ADR 体系？

```
当满足以下任意条件时：
- 团队扩展到 10+ 人
- 项目运行 2+ 年
- 有多个通信受阻的子团队
- 需要向客户展示设计决策历史（合规）
- 有频繁的重构和架构演进
```

## 📊 对比表：各种体系的成本/收益

| 体系 | 初始成本 | 维护成本 | LLM 效率 | 知识转移 | 推荐场景 |
|-----|---------|---------|---------|---------|---------|
| **仅 PRD** | 低 | 低 | 中 | 差 | <1 个月小项目 |
| **PRD + 实施计划** | 低 | 低 | 高 | 中 | ✅ 当前状态 |
| **PRD + ARD + 实施** | 中 | 中 | 很高 | 好 | ⭐ 推荐改进 |
| **PRD + ARD + ADR* + 实施** | 中 | 高 | 很高 | 很好 | 企业项目 |

*ADR = 3-5 条关键决策

## 结论

### 你现在需要做的

1. ✅ 保留：PRD, 实施计划, 实施进度
2. 🆕 补充：**ARD（架构设计文档）** - 这会显著提升 LLM 输出质量
3. ⚠️ 可选：ADR（3-5 条关键决策记录）- 如果决策复杂可选

### 完全不需要做的

- ❌ 详细 ADR 集合（>10 条）- 对你的规模来说过度
- ❌ 详细 C4 Level 3-4 - 浪费时间
- ❌ 完整数据存储库 - 代码注释已足够

### 建议日程

```
Week 1: 创建 ARD 和 ADR templates
Week 2: 填充 ARD（关键决策写 3-5 条 ADR）
Week 3+: 继续项目，按需更新
```
