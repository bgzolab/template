# 项目设计文档

## 文档权威顺序（LLM 读取约束）

1. 归档规范唯一源：`docs/memories/archive-markdown-schema-v1.md`；
2. 其余 `docs/memories/*.md` 仅做边界与上下文补充；
3. `docs/implementation-plans/*.md` 仅用于执行步骤，不作为行为规范来源。

> 注释：当文档冲突时，以 schema v1 为准；若 memories 缺失规则，不允许自动推断。

## 项目简介

本项目是一个 TG 机器人赋能功能，主要是在 TG 上进行一系列功能开发，比如：消息存档、消息转发、多媒体提取等等。

借助 TG 的中转平台，我们很容易就能把本地部署的服务，暴露到公网中，供他人或自己使用。

## 本轮设计冻结决策（2026-02）

1. 配置源固定为 `config/config.yaml`，暂不支持环境变量覆盖配置；
2. 社媒同步触发规则完全由 `socialMediaSync.targetChannel` 控制；
3. 频道匹配规则为**精确匹配**（`sourceId == targetChannel[i]`）；
4. 未命中同步规则时，行为为“日志 + 通知”；
5. `notification` 视为历史遗留配置，后续将完全删除，不再作为设计目标。
6. 归档结构采用“来源优先分桶”，并由 `archive-markdown-schema-v1.md` 唯一定义；
7. 归档改造采用“一次性切换”，是否切换由 schema v1 中的门禁阈值判定。

## 功能设计：消息存档

解析 TG 消息，提取文本、图片、视频等内容，并存储到本地 MD 文件。

### 目标

- 统一归档文本与媒体引用；
- 按来源（用户/频道）进行文件隔离；
- 对重复消息进行基础去重。

## 功能设计：数据库存储

将 TG 消息存储到数据库（SQLITE）中，方便后续查询和分析，同时也要兼顾MD文件的存储。

### 目标

- 记录消息主数据与附件元信息；
- 支撑后续按来源、时间、关键字查询；
- 与文件存档形成可追溯关系。

## 功能设计：社交媒体消息同步

### Why

1. 多个平台发布非常烦，我希望通过一个窗口分发；
2. 多个平台的流量支持，覆盖人群更广；

### What

将某个频道的消息同步到其他社交媒体平台（如Twitter、Mastodon, BlueSky 等），实现跨平台的消息传播。

### How（当前设计）

1. 从消息中解析 `sourceId`（优先频道 username，否则频道 id）；
2. 用 `sourceId` 与 `socialMediaSync.targetChannel` 做精确匹配；
3. 命中后执行平台同步（BlueSky、Mastodon、Twitter）；
4. 未命中则跳过同步，并输出日志与通知消息。

### 非目标（当前阶段）

- 不引入模糊匹配、通配符、正则匹配；
- 不处理环境变量注入配置；
- 不恢复或扩展 `notification` 独立配置块。

## 已知实现偏差（常驻）

> 本小节用于持续记录“设计与实现不一致”的点，修复后应在 `docs/progress.md` 标注关闭。

### 偏差清单

1. 历史配置与运行实例中可能仍残留 `notification` 配置块，但当前代码未消费该配置；
2. 部分配置字段已声明但缺少统一“配置生效矩阵”文档（需在架构/技术栈文档补齐）；
3. 社媒平台错误处理策略仍偏粗粒度（仅成功/失败通知），未做统一重试分级。
