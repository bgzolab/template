## 当前设计目标

项目分两个阶段演进：

1. 先稳定解析 `.venera` 数据包。
2. 再从解析结果中提取 `local_favorite.db` 的目标收藏夹，并通过 Bangumi API 同步收藏状态。

## 已实现设计

### 数据提取层

当前解析器采用“先提取归档，再独立处理数据库”的朴素分层：

1. 归档层：`.venera` 作为 zip 读取。
2. 配置层：`appdata.json` 直接 JSON 解析。
3. 数据库层：将 sqlite 数据库落到临时目录后读取。
4. 输出层：摘要输出和结构化 JSON dump。

这样的分层是合理的，因为后续同步能力只需要消费“结构化收藏记录”，不应关心 zip 和 sqlite 细节。

### 输出设计

当前输出偏向通用调试和观察，不是 Bangumi 专用模型。这是可接受的第一阶段设计，因为它优先保证：

1. 可以验证导出包格式。
2. 可以观察真实表结构。
3. 可以为第二阶段的数据映射提供证据。

### 当前同步实现进度

截至 2026-05-02，Bangumi 同步相关设计已有以下落地部分：

1. `sync-bangumi` CLI 参数形态已固定为 `--sync <table>=<state>`。
2. 已能从 `local_favorite.db` 的指定动态表提取结构化同步候选项。
3. 已有独立的搜索输入模型。
4. 已有本地匹配判定模型，可区分精确命中、零结果、歧义和低置信度。

当前尚未落地的部分：

1. 完整同步编排。
2. 当前收藏状态的幂等判定接线。
3. 幂等更新写入。
4. dry-run 审计汇总。

### 当前 API 集成状态

截至 2026-05-02，已新增最小 Bangumi 客户端设计实现：

1. 从 `ACCESS_TOKEN` 环境变量读取令牌。
2. 统一设置 `Authorization` 和 `User-Agent`。
3. 已能封装 subject 搜索、当前用户收藏读取和收藏写入请求。
4. 已能区分鉴权失败与一般请求失败。

当前唯一未完成的验证是：

1. 需要一个真实有效的 `ACCESS_TOKEN` 来完成正向 smoke test。

## 计划中的 Bangumi 同步设计

### 功能目标

同步功能只处理 `local_favorite.db` 中用户指定的部分动态收藏夹表，例如 `Doing`，并为每个表显式指定 Bangumi 收藏状态，例如：

1. `Doing -> 在看`
2. `DONE -> 看过`
3. 未来也可以扩展到 `想看`、`搁置`、`抛弃`

### 核心约束

#### 1. 没有稳定外键

Venera 的本地收藏记录没有 Bangumi `subject_id`。因此同步前必须执行搜索匹配，而不是直接更新。

这意味着同步系统必须将“搜索”视为显式步骤，而不是内部细节。

#### 2. 搜索结果天然有歧义

仅凭标题、作者、标签进行搜索会出现：

1. 零结果
2. 多结果
3. 同名不同作品
4. 简体、繁体、日文、英文标题不一致

因此自动同步不能采用“第一条命中即写入”的策略。更稳妥的行为应为：

1. 优先精确匹配标题。
2. 将 `name`、`name_cn`、原始搜索词放入同一匹配流程。
3. 利用作者、标签、作品类型辅助过滤。
4. 对多候选或低置信度结果直接跳过并记录原因。

#### 3. 同步是幂等操作

对于每条已成功映射到 Bangumi subject 的记录，应先读取当前收藏状态：

1. 如果目标状态已一致，则跳过。
2. 如果目标状态不一致，则更新。
3. 如果用户尚未收藏，则创建或更新收藏。

幂等性是必须保留的设计目标，否则重跑脚本会产生不可预期行为。

#### 4. Access Token 只通过环境变量输入

认证输入来源固定为 `ACCESS_TOKEN` 环境变量，不从 CLI 参数或配置文件接收令牌。这样可以避免：

1. 令牌出现在 shell history。
2. 令牌被误写入仓库文件。
3. 计划外的多处配置源。

### Bangumi API 交互边界

依据 Bangumi API 文档和服务端源码，当前设计以以下事实为前提：

1. 新版 API 通过 `Authorization: Bearer <token>` 传递令牌，不再接受 query string token。
2. 非浏览器客户端应携带可识别的 `User-Agent`。
3. 搜索 API 可按关键词搜索 subject。
4. 用户收藏状态存在合法枚举值 `1..5`，分别对应 `想看 / 看过 / 在看 / 搁置 / 抛弃`。
5. 用户 subject 收藏存在查询与更新能力。

实施时仍需用最小 smoke test 对实际请求路径和响应体做最终确认，因为公开文档页面本身较难直接抓取。

## 建议的数据流

后续同步命令建议采用如下流水线：

1. 读取 CLI 参数。
2. 校验 `ACCESS_TOKEN`。
3. 解析 `.venera` 归档。
4. 从 `local_favorite.db` 中加载目标表。
5. 将 Venera 记录转换为候选同步项。
6. 对每个候选项执行搜索。
7. 对搜索结果执行匹配决策。
8. 查询当前 Bangumi 收藏状态。
9. 根据幂等规则决定跳过或更新。
10. 输出成功、跳过、失败三类结果汇总。

## 当前不纳入范围的内容

以下能力在本轮计划中明确排除：

1. 自动同步 `history.db` 的阅读进度或章节进度。
2. 自动同步评分、评论、标签。
3. 自动维护 Venera 记录与 Bangumi subject 的本地持久映射缓存。
4. 交互式人工确认 UI。

先把“指定收藏夹表 -> 搜索 -> 幂等更新收藏状态”打通，才有资格扩展更多字段。
