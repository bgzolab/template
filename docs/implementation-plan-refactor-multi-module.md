# 多模块重构实施计划（阶段1：文档先行）

## 1. 背景与目标

当前 `main.go` 聚合了启动、消息处理、归档、数据库写入、社媒同步、通知等多类职责。为满足后续扩展（新增平台/新增处理节点）与可测试性要求，本计划采用“先文档定边界，再小步改代码”的方式推进重构。

本次仅执行**阶段1（文档落地）**，不进入代码重构。

## 2. 冻结决策（已确认）

1. 公共数据结构继续沿用 `internal/Entity`；
2. 去重策略优先数据库唯一约束，应用层检查作为补偿；
3. 执行模型采用“串行到异步分阶段”；
4. 配置源固定为 `config/config.yaml`；
5. 社媒同步触发由 `socialMediaSync.targetChannel` 精确匹配控制。

## 3. 范围与非目标

### 范围（阶段1）

- 完成重构实施文档；
- 完成技术规范补充；
- 完成进度记录与架构洞察更新；
- 产出进入阶段2所需的门禁与验收清单。

### 非目标（阶段1）

- 不修改业务代码；
- 不调整数据库结构；
- 不新增运行时依赖；
- 不改变当前线上行为。

## 4. 目标架构（文字化）

### 分层规划

1. **入口层**：只保留 CLI 启动与依赖装配；
2. **Pipeline 层**：`preprocess -> archive -> sync -> notify`；
3. **Service 层**：
	- ArchiveService：处理归档与持久化编排；
	- SyncService：处理同步策略判定与分发；
4. **Adapter 层**：对接 Telegram、文件系统、SQLite、社媒 API；
5. **Entity 层**：跨模块共享结构与配置对象（沿用 `internal/Entity`）。

### 扩展预留

- 新增社媒平台通过 Provider 接入，不改核心 pipeline；
- 串行稳定后再引入异步执行。

## 5. 分阶段实施路线

### P0（当前执行）：文档落地与门禁建立

目标：冻结规则、明确边界、定义测试与准入门禁。

### P1（待批准）：代码结构拆分（保持串行）

目标：拆分 `main.go` 责任边界，归档与同步解耦但仍串行执行。

### P2（待批准）：异步化与插件化增强

目标：在不破坏 P1 行为前提下，将同步阶段从串行演进为异步并支持 Provider 扩展。

## 6. 阶段1执行步骤（逐步 + 独立测试）

### 步骤1：补全本实施计划文档

- 测试：核对是否包含第 1~10 节全部章节标题；
- 通过标准：章节完整、无占位注释残缺。

### 步骤2：更新技术规范文档

- 动作：在 `docs/tech-stack.md` 增加重构执行规范（Entity 统一、DB 唯一约束优先、串行到异步、测试纪律）；
- 测试：逐条检查规范是否可执行且与冻结决策一致；
- 通过标准：至少 8 条规范，且不与现有配置生效矩阵冲突。

### 步骤3：记录阶段1进度

- 动作：在 `docs/progress.md` 记录阶段1完成项、产出物与下一步门禁；

- 通过标准：后续开发者可据此判断改动落点。

## 7. 第2步准入门禁（9项全通过）

仅当以下 9 项全部通过，才允许开始阶段2（代码改造）：

1. `docs/implementation-plan-refactor-multi-module.md` 章节完整且无占位缺失；
2. 冻结决策 1~5 在实施计划中表述一致；
3. 分阶段路线（P0/P1/P2）明确且无冲突；
4. 每个阶段至少有 1 条可执行验证方法；
5. `docs/tech-stack.md` 已新增重构执行规范并与冻结决策一致；
6. 技术规范明确“去重优先数据库唯一约束”；
7. 技术规范明确“执行模型串行到异步分阶段”；
8. `docs/progress.md` 已记录阶段1产出与下一步门禁；
9. `docs/architecture.md` 已新增重构期文件职责洞察。

> 门禁规则：9/9 全通过 + 用户明确批准，才进入阶段2。

## 8. 风险与回滚

1. 风险：文档术语不一致会导致后续拆分方向偏移。  
	回滚：回退到冻结决策表，以冻结决策为唯一准绳修订文档。

2. 风险：阶段定义过粗，无法执行小步验证。  
	回滚：将阶段任务细化为“单文件/单职责/单验证”。

3. 风险：测试定义不可操作。  
	回滚：补充“执行方式 + 通过标准 + 失败处理”三元描述。
